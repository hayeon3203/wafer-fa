# Dedicated warm-process prediction server, not the Streamlit app, drives ThingsBoard-triggered runs

Phase 2.5.4 adds a "run a random wafer through the full pipeline" button inside ThingsBoard, with a 5-stage progress bar. Both LLaVA and DINOv2 are cached as module-level globals and only warm up on first call, so whichever process runs a pipeline pays the ~14GB LLaVA load cost once and then stays warm — running it in two processes at once doubles that GPU memory. We considered leaving `app.py`'s relay button in place alongside a new ThingsBoard-facing server and relying on the operator to never run both at the same time, but rejected it: that's a rule a person has to remember forever, and forgetting it means an OOM mid-demo. Instead, a new standalone server (`wafer_predict_server.py`, following the existing `wafer_browser_server.py` pattern) becomes the *only* process allowed to hold the warm models, and the relay-running code is removed from `app.py` entirely rather than left dormant.

Because the pipeline can take several seconds per stage, the server accepts a run request with an in-flight lock (409/ignored if one is already running), returns immediately, and reports progress purely through ThingsBoard telemetry (`pipeline_stage`, pushed once per stage as each one starts, plus `idle` before a run starts and `error` if one fails) rather than a blocking HTTP response or a separate status-polling endpoint. The progress widget has no other source of truth — it derives every box's color from comparing its own stage index to the latest `pipeline_stage` value.
